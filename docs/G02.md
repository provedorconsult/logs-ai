## Configuração do recurso Dokploy

1. No projeto autorizado, configurar um recurso **Compose** para este repositório,
   branch `main`, arquivo `docker-compose.yml`, com build da aplicação. O host
   pode operar Swarm; este procedimento usa o modo Compose do Dokploy. Em modo
   Stack/Swarm, publicar uma imagem no registry e definir `APP_IMAGE` imutável:
   `docker stack deploy` não executa o build nem aguarda `depends_on`.
2. Definir `POSTGRES_PASSWORD` em armazenamento protegido, usando valor aleatório
   hexadecimal. Configurar domínio/proxy reverso para o serviço `app`, porta 8000,
   ou bind em IP Tailnet especificamente autorizado. Não publicar PostgreSQL.
   A porta do host permanece em loopback por padrão.
3. Associar o build ao commit implantado: configurar `APP_REVISION` com o SHA
   exato como argumento de build. O endpoint saudável envia `X-App-Revision`.
   Não considerar um HTTP 200 de uma versão anterior como validação desta entrega.
4. Confirmar na documentação da instância os contratos `compose.one`,
   `compose.update`, `compose.saveEnvironment` e
   `POST /api/compose.deploy`, payload `composeId` e header `x-api-key`. Só então definir
   `DOKPLOY_API_CONTRACT_VERIFIED=true`; o cliente não descobre nem provisiona
   recursos automaticamente e não deve receber o ID de outro projeto.
5. Fornecer `DOKPLOY_URL`, `DOKPLOY_COMPOSE_ID`, `DOKPLOY_PROJECT_ID`, `DOKPLOY_API_TOKEN` e
   `APP_TEST_URL` ao ambiente seguro. HTTPS deve validar certificado e hostname;
   HTTP é aceito em loopback com túnel SSH validado e
   `DOKPLOY_SSH_TUNNEL_VERIFIED=true`. A chave permanece fora do repositório.
   A decisão humana de 13/11/2026 também autorizou HTTP direto na Tailnet para
   esta G02: configurar `DOKPLOY_ALLOW_TAILNET_HTTP=true` e a origem exata em
   `DOKPLOY_TAILNET_HTTP_ORIGIN`, com hostname `.ts.net`. Não aceitar redirects.
   O cliente também aceita o token da variável local protegida `dokploy_token`.

Para banco externo já provisionado, adaptar a configuração de homologação para
injetar `DATABASE_URL` protegido e retirar a dependência do serviço PostgreSQL
local. Não reutilizar o banco administrativo do Dokploy para dados da aplicação.

## Pipeline

`.github/workflows/delivery.yml` roda em PRs e pushes para `main`:

1. Sincroniza dependências pelo lock, roda Ruff e testes com PostgreSQL descartável.
2. Confere a exportação de dependências e constrói a imagem com SHA do commit.
3. Sobe o Compose descartável e verifica HTTP; remove somente os volumes desse
   projeto efêmero de CI.
4. Quando `ENABLE_DOKPLOY_CD=true`, dispara o recurso Dokploy e verifica readiness
   e `X-App-Revision` no servidor de testes. O job usa runner dedicado com labels
   `self-hosted, logs-ai-deploy` e ambiente GitHub `homologacao`. Ele só roda em
   `main`, após CI aprovada, nunca em código de PR.

Configurar as variáveis do passo anterior em GitHub Variables, token em GitHub
Secrets e acesso de rede no runner. O runner precisa de Python 3; se usar túnel,
este deve estar estabelecido e validado antes do job, sem interação. Desabilitar
webhook paralelo de auto-deploy que contorne CI. O Dokploy deve buscar o mesmo
commit verificado; se `main` avançar e o build buscar outro SHA, o teste de revisão
falha e exige reconciliação, não registra sucesso indevido. O cliente confere
projeto, repositório e branch, preserva os segredos existentes e atualiza
`APP_REVISION` e `APP_IMAGE` com `EXPECTED_REVISION` (SHA completo). O cliente
confere o checkout local e publica uma tag exclusiva `logs-ai-deploy-<SHA>`,
sem sobrescrever referência existente. O Dokploy busca essa tag para que avanço
de `main` durante a entrega não mude o código construído. O cliente exige Git
no runner e permissão de push de tags; o job remoto tem `contents: write`.
O recurso deve usar GitHub integrado ou Git HTTPS deste repositório, modo
Compose, `docker-compose.yml`, `autoDeploy=false` e fonte `main` inicialmente,
depois a tag do SHA promovido. O comando permanece o padrão Compose da instância,
sem operadores de shell (rejeitados pelo Dokploy v0.31.1). O override `command`
fica vazio; o preview retornado por `compose.getDefaultCommand` inclui o binário
`docker`, mas o override espera argumentos, e não deve receber esse preview.

Sem runner/configuração, o job remoto é pulado explicitamente; a existência do
workflow não comprova deploy. Para disparo manual com o mesmo ambiente seguro:

```sh
python3 scripts/deploy.py
python3 scripts/check_health.py
```

Definir `EXPECTED_REVISION` para o SHA esperado ao implantar e validar a entrega.
A confirmação HTTP da API significa pedido aceito, não conclusão do deploy.
Não há rollback automático: em falha, seguir o harness e avaliar schema/backup.

## Critério de aceite remoto

Hermes e Devs Humanos devem verificar versão implantada, instância saudável,
`pg_isready`, conexão autenticada, migrations, `/health` HTTP 200 com banco ativo,
logs sanitizados e persistência. Em Swarm, exigir `1/1`; em Compose, verificar
contêiner e healthcheck. Aplicar [HARNESS.md](HARNESS.md). O Maker não substitui
o Checker independente nem declara aprovação com base apenas em testes locais.
